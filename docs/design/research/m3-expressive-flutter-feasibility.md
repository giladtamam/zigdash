# Material 3 Expressive and Flutter feasibility for the ZigDash redesign

Resolves `tickets/02-research-m3-expressive-flutter.md`. Written 2026-09-26.

**Question.** What identity latitude does Material 3 give a Flutter app without leaving it, on the Flutter this repo runs (3.32.5, Dart 3.8.1) versus current stable (3.47.x; the caller states 3.47.5, hotfix number not verified here)?

**Answer in one paragraph.** Every primitive the redesign would lean on — per-component shape theming, squircle and polygon tile shapes, directional (RTL-safe) radii, a custom type scale with M3 "emphasized" weights, seed-scheme variants and contrast levels, harmonized custom colors, M3 easing/duration tokens and spring physics with the M3 Expressive spring values — is present in Flutter 3.32.5 (verified by grepping the installed SDK source). What is *not* available on either version is the Material 3 Expressive **component** set (button groups, split button, FAB menu, loading indicator, toolbar) and the 35-shape library with first-party morphing: the in-SDK Material library was frozen in 3.44 and the Flutter team says Expressive work happens only in the new standalone `package:material_ui`, which today (1.4.0, requires Flutter 3.47) exposes only a `StyleVariant.material3Expressive` flag and none of those components. So the feasibility table is the same on 3.32.5 and 3.47.x; the upgrade question is a maintenance-and-timing question (frozen library, deprecation announced for the November stable, golden baselines), not a design-latitude question. One real defect surfaced: with dynamic color on, this app's `dynamic_color` 1.8.1 does not populate the `surfaceContainer*` / `*Fixed` roles, so every tonal surface collapses to `surface`; `dynamic_color ^1.9.0` fixes it and resolves on 3.32.5.

## Feasibility table

## What this means for tickets 06 and 07

- **Concept "close to stock Material You"** costs nothing beyond rows 1 and 5 (variant/contrast on the fallback scheme, fixing the surface-role defect). Fully affordable on 3.32.5.
- **Concept "stronger identity layer"** is affordable if it is built from rows 1–4, 6, 7: squircle or rounded-polygon tiles with `StarBorder`/`RoundedSuperellipseBorder`, directional radii, an emphasized type scale, a harmonized brand accent and brand-defined state colors, spring motion from the M3 token values. It is **not** affordable if it depends on Google's 35-shape library, first-party shape morphing, or any Expressive component (row 9) — those would be hand-built, and they would be re-done when `material_ui` ships them. Design the signature color as a harmonized accent/tertiary role, never as a replacement `primary` on the wallpaper scheme.
- **Concept "wall-tablet"** has no framework blocker; the cost is layout work (grid columns, touch targets) plus the golden matrix for tablet widths (row 8). Squircles will not show in web-build screenshots (row 2).
- **Tokens (07)** should be expressed as: shape tokens per component class mapped onto `ThemeData` component themes; a `TextTheme` override with emphasized weights; a `ColorScheme` extension for state roles built with `harmonizeWith(primary)`; a spring/easing token class; all directional. Decide explicitly how per-dashboard seeds interact with dynamic color (replace vs harmonize).
- **Guardrails (09)** should sequence: (upgrade decision) -> baseline goldens with alchemist two-tier -> redesign PRs diffed against them.

## For and against upgrading before the redesign

**Against (no design lever needs it):** every primitive above exists in 3.32.5, verified in the installed SDK source; nothing Expressive ships in 3.47's in-SDK Material either; `material_ui` 1.4 adds only a flag; the third-party Expressive package is immature. The feasibility table is identical on both versions, so tickets 06/07 are not blocked by the upgrade.

**For (do it as its own engineering ticket, before golden baselines):** the library the redesign will theme is frozen at 3.44 and slated for deprecation in the November stable, so staying on 3.32.5 means writing theme code against a library that must be migrated anyway; `dynamic_color` 2.x and every future first-party Expressive piece gate on 3.47 + `material_ui`; golden baselines created on 3.32 are thrown away at the next upgrade; the known migration costs are small and enumerable (row 10). Recommendation: upgrade to 3.47.x (optionally straight to `material_ui` via `dart fix`) as a discrete ticket, then baseline goldens, then land redesign phases; do not let it block direction exploration.
